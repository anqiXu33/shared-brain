# Database schema

shared-brain stores everything in one Postgres database (Supabase free tier) with two extensions:
**pgvector** for embeddings and **pg_trgm** for keyword matching. The server never runs an LLM;
the database holds the memories, their history and the project registry, and two SQL functions
do all the ranking.

This page describes the schema as it stands after `schema.sql` and migrations 001 to 006, how it
got there, and how search ranks results.

## Tables

```text
projects                     memories                                memory_history
────────                     ────────                                ──────────────
name (pk) ◄───────────────── project      (fk, on update cascade)
description              ┌─► id (pk) ◄────────────────────────────── memory_id (fk, on delete cascade)
aliases text[]           └── superseded_by (fk, on delete set null)   old_content
created_by                   valid_until                             old_source
created_at                   content, kind, tags, source             replaced_at
                             embedding, embedding_model
                             created_at, updated_at
```

### `memories`

One row is one self-contained statement, for example "my-site: decided on Astro because the content is static".

| Column | Type | Meaning |
|---|---|---|
| `id` | `uuid` | Primary key, generated by the database. |
| `content` | `text` | The memory itself. |
| `project` | `text` | Which project it belongs to. Foreign key to `projects.name` (migration 005). |
| `kind` | `text` | One of `state`, `decision`, `blocker`, `context`, `log`, `session-summary` (migration 002, default `context`). |
| `tags` | `text[]` | Optional finer categories, e.g. `{evaluation, cv}`. |
| `source` | `text` | Which client wrote it: `claude-web`, `chatgpt`, `claude-code`, … Any non-empty value since migration 002. |
| `superseded_by` | `uuid` | Set when a newer memory replaced this one (`save_memory(..., supersedes=id)`). |
| `valid_until` | `timestamptz` | When the memory stopped being true: set on supersede and on `retire_memory`. |
| `embedding` | `vector(1536)` | OpenAI `text-embedding-3-small`, computed by the server on save and on content edits. |
| `embedding_model` | `text` | Which model produced `embedding`, so a future model change can re-embed selectively. |
| `created_at`, `updated_at` | `timestamptz` | Set by the database / by the server on edits. |

A memory is **active** when `superseded_by is null and (valid_until is null or valid_until > now())`.
Search, `recent_memories` and `project_brief` show only active memories unless asked for history.

The six kinds age differently, which is why they are a column rather than a tag:

| Kind | What it holds | How it ends |
|---|---|---|
| `state` | Where something currently stands | Superseded by the next state |
| `decision` | A choice and its reason | Superseded if the decision changes |
| `blocker` | An open problem | Retired when solved |
| `context` | Background that rarely changes | Usually never |
| `log` | A one-off progress note | Never; it is history by nature |
| `session-summary` | What one working session did | The next summary of the same session supersedes it |

Indexes: HNSW on `embedding` (cosine), GIN trigram on `content`, B-tree on `project` and on `(project, kind)`.

### `memory_history`

Old wordings of memories that were edited in place with `update_memory`. Rows are written by a
`before update` trigger on `memories` whenever `content` actually changes, so no client can forget
to archive. Deleting a memory deletes its history (`on delete cascade`).

Superseding is different from editing: it creates a new row and leaves the old one untouched, so
the old one stays in `memories` with `superseded_by` set. `memory_history` is only for corrections.

### `projects`

The registry of project names. Every memory must point at a registered project (foreign key), so
assistants cannot quietly split one project into `scai`, `scai-lab` and `SCAI`.

| Column | Meaning |
|---|---|
| `name` | Lowercase letters, digits and hyphens, 2 to 40 characters (`check` constraint). |
| `description` | One sentence, so an assistant can tell where a memory belongs. |
| `aliases` | Other names the user uses: `{心力球, AI挂件}` for `ai-pendant`. The server resolves them; it also keeps an alias from pointing at two projects. |
| `created_by` | Which client registered it, or `migration` for names backfilled by migration 005. |

Renaming a project (`update projects set name = ...`) carries its memories along (`on update cascade`).

## How the schema evolved

Every migration is additive and safe to run while the previous server version is live; each
file's header explains how to roll it back (`schema.sql` is the starting point and has none). They are applied by hand in the Supabase SQL editor,
in order. CI applies `schema.sql` and all migrations to a fresh database on every push.

| Step | What changed | Why |
|---|---|---|
| `schema.sql` | `memories` with content, project, tags, source (limited to three values), embedding. RLS on. `match_memories()`: nearest neighbours within one project. | Stage 1: save, search, and a duplicate check before saving. |
| `001_history` | `memory_history` table and the archiving trigger. | Edits overwrote text with no way back. |
| `002_kinds_validity_hybrid` | Full backup tables first. `source` opened to any non-empty value. `kind` column, backfilled from existing tags. `superseded_by` and `valid_until`. `pg_trgm` and a trigram index. `match_memories()` ignores inactive memories. New `search_memories()` with hybrid ranking. | Statuses went stale and were overwritten instead of replaced; exact names such as library names ranked poorly with vectors alone; new clients needed a schema change just to write. |
| `003_eval` | `eval_rank_memories()`: both raw scores for every active memory of a project. Read-only. | The retrieval evaluation reproduces vector-only, keyword-only and hybrid ranking offline from these scores. |
| `004_deterministic_ties` | `search_memories()` ranks deterministically: ties in the vector and keyword lists are broken by vector distance, then id; the final order by fused score, then most recently updated, then id. | The evaluation showed short queries give many memories the same keyword score, and Postgres ordered those ties arbitrarily, so results changed between identical calls. |
| `005_projects` | `projects` table, backfilled from the project names already in use; foreign key from `memories.project`. | The allowed-project list lived in an environment variable and needed a redeploy to change. |
| `006_project_aliases` | `projects.aliases text[]`. | Users call projects by nicknames in several languages; resolving them in one place means every assistant understands the same nickname. |

## Search

### `search_memories()` (hybrid)

Called by the `search_memory` tool and by the viewer's search box.

```sql
search_memories(query_embedding vector(1536), query_text text, filter_project text,
                match_count int = 5, filter_kinds text[] = null, include_inactive boolean = false)
```

1. **Pool.** Memories of `filter_project`, optionally only certain kinds, and only active ones
   unless `include_inactive`. For each: cosine distance to the query embedding, and
   `word_similarity(query_text, content)` (pg_trgm, 0 to 1: how completely the query's words
   appear somewhere in the content).
2. **Two ranked lists.**
   - Vector: the 30 closest by distance.
   - Keyword: the 30 highest `word_similarity`, only those at 0.3 or above.
   Ties are broken by vector distance, then id (migration 004), so the same query always gives the same order.
3. **Reciprocal rank fusion.** Each memory scores `1/(60 + rank)` in every list it appears in;
   the two are added. A memory near the top of both lists beats one that tops only one.
   RRF uses ranks, not raw scores, so the two very different score scales never need calibrating.
4. **Result.** The top `match_count` by fused score (ties: most recently updated, then id), with
   `similarity`, `keyword_score` and the fused `score` returned for inspection.

Why both: on the evaluation set (52 queries, see the README) vectors alone already *find* exact
names and short Chinese queries, but rank them lower; the keyword list pulls them to the top.
Hybrid ranking raised MRR from 0.801 to 0.854.

### `match_memories()` (duplicate check)

Nearest active neighbours by cosine similarity within one project. `save_memory` calls it before
inserting; at similarity 0.9 or above (`DEDUP_THRESHOLD`) nothing is saved and the existing memory
goes back to the assistant, which decides whether to supersede, edit or reword. The server does not
merge anything by itself.

## Access and security

- **Row Level Security** is on for every table, with no policies. The public `anon` key sees
  nothing; only the server's `service_role` key can read or write.
- The functions run with the caller's rights (not `security definer`). The search functions
  (`match_memories`, `search_memories`, `eval_rank_memories`) pin `search_path`; the history
  trigger function from migration 001 does not, which is harmless while it is not `security definer`.
- The MCP endpoint lives at a secret URL path (`MCP_SECRET_PATH`).
- The web viewer (`/viewer`, see `viewer.py`) is off unless `VIEWER_TOKEN` is set. It only reads:
  no route in it inserts, updates or deletes, which the tests check. It does use the same
  `service_role` connection as the server, so the guarantee comes from the code rather than from a
  separate database role.
- Backup tables from migration 002 (`*_backup_002`) are RLS-protected copies and can be dropped
  once you no longer need them.
